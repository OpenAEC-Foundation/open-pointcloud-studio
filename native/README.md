## Workspace

The workspace has two crates:

- `core` (`pointcloud-core`, LGPL-3.0-or-later): readers and writers of the file formats, the octree index on disk, streamed reads of the source and of the index, export, the meshers, the 2D drawings of a section box, the caps that fill the cut of a mesh by a section box (`section_caps.rs`), face detection and the 3D BAG client. It has no user interface.
- `desktop` (`open-pointcloud-studio-native`, GPL-3.0-only): the `iced` application with its `wgpu` viewport, the tools, among them box selection and point picking (`selection.rs`), the settings, the local command API and the MCP server. Its binary is `open-pointcloud-studio`.

The version is written once, under `[workspace.package]` in `Cargo.toml`. No HTML, CSS, JavaScript or web view is used.

## Running and testing

```bash
cd native
cargo run -p open-pointcloud-studio-native                      # the window
cargo run -p open-pointcloud-studio-native -- /path/to/scan.laz # with a file
cargo run -p open-pointcloud-studio-native -- --help            # every command-line mode
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

A development build compiles `pointcloud-core` and the `las` and `laz` crates with optimisation (see the profiles in `Cargo.toml`), so that large scans stay usable while developing. The full-source loops of the readers, the exporters, the meshers, the section drawing and the face detection live in `core` for that reason: the desktop crate passes in predicates and progress callbacks and does not recompile those loops at its own lower optimisation level.

Four benchmarks are examples of the core:

```bash
cargo run -p pointcloud-core --example visit_bench -- FILE 2000000   # read the first points of a file
cargo run -p pointcloud-core --example lod_bench -- FILE.laz 80000   # a level-of-detail sample from an index
cargo run -p pointcloud-core --example surface_bench -- FILE.laz OUTPUT.obj
cargo run -p pointcloud-core --example closed_mesh_bench -- FILE.e57 # the stages of the closed mesher, timed
```

Test data is generated by the tests or comes from public data sets. [TEST_DATA.md](TEST_DATA.md) lists the public ones and how to fetch them. Nothing of a real project goes into the repository: no scans, no screenshots of them, no file names or places. The one exception is the picture at the top of the root README, which shows a scan of the maintainers' own building and was put there by them.

Tests that hold documents to the code:

- `cli_help.rs`: the list of command-line modes against what `main` handles, and the table in the root README against that list.
- `mcp/tests.rs`: every command listed in `API.md` has an MCP tool, and `MCP.md` lists exactly the tools, in order.
- `i18n.rs`: every translated text in the source has an entry in every language table, and no entry is unused.

The two tests marked `live_services` ask the real 3D BAG and map services and are skipped by default; [TEST_DATA.md](TEST_DATA.md#checking-the-3d-bag-and-map-services-before-a-release) says when to run them.

Each file states its source and what was changed. OpenCADStudio is GPL-3.0, so the desktop crate is GPL-3.0-only; the licence text is [`desktop/LICENSE-GPL-3.0`](desktop/LICENSE-GPL-3.0). The core stays LGPL-3.0-or-later.

Colours, group captions, active and hover states and the Settings dialog follow the [OpenAEC style book](https://github.com/OpenAEC-Foundation/OpenAEC-style-book). ## User interface

- **Ribbon.** All tools are on one ribbon without tabs, and every action appears there once. Small tools stand in three rows. The ribbon measures its scrollable content, so the arrow buttons appear only when groups are cut off and go away when the window is wide again. The cancel action of a running selection, scale or index build takes the place of its start button or appears only during the job; the one button of the SURFACE group, Mesh Pointcloud, says while a job of its methods runs how far it is, and its card has the cancel. The block of the Section drawing tool comes first in Properties, so that it is in view when its ribbon button is pressed.
- **Rarely used commands** are in the File view (`file_view.rs`). Properties holds the settings and the lists of what is in use; of the ribbon's actions it repeats only Save for a view, Clear for a measurement and the cancel button of a running mesh or scale job. The settings of the meshers are not in Properties but on the card of Mesh Pointcloud; Properties keeps the figures of their results with the scan.
- **Texts.** A text is written in English in the source and passed through `i18n::tr`; `i18n::key` marks a text that is translated where it is shown. Other languages are tables from the English text in `assets/locales/`, and a text without an entry stays English. A counted text is an entry with `{name}` marks that are filled in when it is shown; a translation keeps the same marks. A further language is one JSON file beside `nl.json` and one line in the table of `desktop/src/i18n.rs`; only the `set_language` rows of `API.md` and `MCP.md` name the language codes by hand. Status messages are not translated.
- **Settings files.** `preferences.rs` reads and writes `settings.json` (colour mode, point size, eye-dome switch and strength, station markers, point budget, auto-index). A change from the ribbon or the API is saved after a short delay, and invalid stored numbers fall back to the defaults. The theme and the language are each one small file, and `extensions.json` lists the extensions that are switched off and the installed extensions with their versions, so a missing or damaged file enables everything and installs nothing. The user guide names the folders.
- **Extensions** (`extensions/`). An installed extension is a folder in `extensions/<id>/` of the settings folder, checked by `manifest.rs` (the `extension.json`, its icons and the folder) and installed by `install.rs` from a folder or a `.zip` through a staging folder after the user confirms. `run.rs` starts its program as a process of its own with the port and a token of the local API for that run, writes its output to a log per run and ends it and what it started when it is stopped or the window closes (a job object on Windows, a process group elsewhere, also after the program itself ended); a run that ends by itself releases its job, so what it opened stays. The server of `native_api.rs` accepts the token of a run for the commands the extension declared and hands its requests to the window with the id of the extension. `page.rs` draws the Extensions page, the dialogs, the EXTENSIONS group of the ribbon and the runs in the status bar. [docs/extensions.md](../docs/extensions.md) is for authors.
- **Window.** On X11 the application sets the light or dark hint of the system title bar to match the theme; on Windows the title bar takes the colours of the theme (`native_chrome.rs`). On Linux the window announces the application id `org.openaec.OpenPointcloudStudio`, the name of the desktop entry. On macOS, files handed over by the system are opened like dropped files (`macos_open.rs`).
- **Dialogs.** File dialogs use `rfd::AsyncFileDialog`, so the window stays responsive while the dialog of the system is open.
- **Layer identity.** Preview and index jobs, meshing, deletion and Undo and Redo are matched to the layer they belong to, not to its file path.

## Reading and writing

- LAS and LAZ open from the header, with a bounded preview that samples spaced ranges without decoding every point. Other formats are read in full once to learn bounds and counts. At most 100,000 preview points are kept per file; a source of 512 MiB or more that is shown while it is read keeps up to two million.
- Full reads of LAS and LAZ use bounded batches: 400,000 points per request for LAZ, so that the parallel decompressor handles several compression chunks at once, and 16,384 for LAS. Callbacks still receive the points in source order and can cancel inside a batch.
- LAZ is written with the parallel compressor of the `las` crate in batches of 400,000 points. A same-format LAS or LAZ export without edits copies the source bytes. Conversions and filtered or transformed exports write the original LAS point records and keep the coordinate grid of the source.
- XYZ, PTS, CSV and both PLY variants are encoded in batches of 65,536 points on several threads and written in source order.
- Every export writes to a temporary file and publishes it under its name only after the whole source and the expected point count have been checked.
- E57 files are read through a buffered window (`window_reader.rs`), because the format is decoded in pages of 1 KiB and a seek per page is slow on a network share. `e57_quick.rs` takes the spread preview of a large file from evenly spaced data packets; `e57_parallel.rs` decodes a scan of the same layout in runs of packets on several threads and hands the points on in file order, the same points as one thread; `snapshots.rs` shows a large source while it is being read.
- `turns.rs` puts large E57 scans that `e57_parallel.rs` can decode on several threads in queues: one per disk for reading, joined when a scan is opened, so that the next scan of a disk is read when the one before has been, and one for the octrees built in the same pass, joined when a scan has been read, so that they are built one after another, in the order the scans were read, while the next scan is read. Other sources take no turns.
- The filtered E57 writer copies the selected raw records with the prototype and value types of each source scan. A new E57 file from another format, or a transform that cannot keep a valid scan pose, is written as one scan in world coordinates with XYZ, 8-bit colour and intensity.
- PCD `VIEWPOINT` rotates and translates every point in all three storage modes.
- A scan project file is a ZIP container whose XML document lists the scans; `project_open.rs` reads only that document, and reads folders and project files on a worker thread.
- The BCF file is a ZIP container written by the application itself (`bcf.rs`), with deflated XML and stored images.

## The index on disk

- The octree is built on several threads. A node is read in blocks of 65,536 of its fixed 40-byte records, which are assigned to the eight children in parallel and written in block order. Subtrees are built side by side on a bounded pool; large nodes are split one at a time so that the disk does not hold every level at once. The files are identical to those of a single-threaded build, which the tests keep as a reference, with exact source ordinals and cancellation between blocks.
- A finished index of a PLY, E57, PCD, PTX, XYZ, ASC, TXT, CSV or PTS file keeps the exact bounds, the count and the attribute flags of the source in a cache manifest that is written atomically. Reopening an unchanged file reads that manifest and a small preview from the octree instead of the source. A missing, stale or damaged manifest falls back to the full reader.
- E57 scanner positions come from the metadata of the file and PCD `VIEWPOINT` from its text header; neither needs point records. PTX scanner positions and axes are stored in the manifest, because each scan block has its own pose.
- `--index` on a file other than LAS or LAZ collects the preview and the metadata while it writes the root of the octree, in one pass over the source. With automatic indexing on, the window takes the same route for such sources of 64 MiB or more and shows the checked preview after that pass while the tree is still being built.
- Each leaf has a compact preview for level-of-detail reads. An index without them creates them on first use.
- A cancelled build removes its temporary files and publishes nothing.

## The 3D view and level of detail

- Points are drawn as lit sphere impostors with `wgpu`. Each sphere writes its curved front surface to the depth buffer, and point picking uses the displayed radius and that depth. Coordinates are rebased in double precision before they go to the graphics card.
- Mesh faces are lit with interpolated vertex normals; a mesh without normals gets them from its triangles, and a non-uniform or mirrored scale maps them into the scene.
- Eye-dome lighting is a screen-space pass that shades points and faces by the depth of their neighbours.
- The viewport keeps its geometry and its uploaded buffers across redraws that only move the camera. A change of visibility, level-of-detail points, colours, filters, edits or section limits rebuilds the points. Points are uploaded in buffers of at most two million each. The buffers of the meshes have a key of their own (`MeshKey` in `gpu_viewport.rs`: every mesh that is switched on, the transform of its layer and the centre of the scene) and are built and uploaded again only when that changes, so a mesh at the limit, 192 MB of vertices and 96 MB of indices, is not rebuilt with every refinement of the points; normals derived for a mesh without them are computed in that build only.
- Where the section box cuts the meshes, the caps over the cut (`section_caps` in the core: pairs of opposite faces along lines in eight directions over each face of the box, gathered on a fine grid) are made on a worker thread named `section caps` and drawn from a vertex and an index buffer of their own (the `section caps` `MeshUpload`), with the mesh pipeline, flat because they carry no normal. Their key (`CapKey`: the `MeshKey` of the meshes, the section box and the colour and largest thickness of the fill) decides when they are made again: a turn of the camera keeps them, a change of the box, the meshes or the fill does not. The cut shows open until they arrive. One job runs at a time, so a box that is dragged gets the caps of where it stands once the earlier ones are done. `section_fill::CapJobs` counts the jobs from their start to the end of their thread; `status.result.section_fill.pending`, `wait_until_idle`, `screenshot` and the snapshots of views read it. It does not depend on frames, which a minimised window, or a 3D view that the Drawing view or the File view replaced, does not get.
- After the camera stops, the viewport chooses the visible octree nodes by their size on screen and reads a sample of at most the point budget. The sample on screen stays until its replacement is ready, and a request that the camera has overtaken is cancelled while it reads. Releasing a drag starts the request for the new view at once.
- Indexed clouds share the budget by how much of the screen each covers, and what one cloud cannot use goes to the others. The clouds are sampled in parallel on a bounded pool.
- For a budget above 500,000 points a first pass is read before the full sample. Its size comes from the read and build pace measured on this computer, with 250,000 points as the least (`lod_pace.rs`), and stays within what the nodes in view give from their previews. It is shown only when it improves on the sample on screen and is skipped otherwise.
- At 20 times zoom or closer the leaves in view are read exactly and only the points that fall inside the viewport are kept. A view that would need more than two million candidate points keeps the regular sample.
- Box selection visits the source points in the octree leaves that the box touches, or reads the whole source when there is no index. A selection is a compact bit set of source ordinals and keeps its bounds in source coordinates, so that Zoom selection needs no second read. Opening, hiding or removing a layer cancels a selection scan that is under way.

## Meshers

- **Terrain** (`mesher.rs`): every source point goes through a bounded grid in X and Y that keeps the lowest point per cell; the result is triangulated as a 2.5D mesh and long edges across gaps are rejected. The cap is 100,000 vertices.
- **3D surface** (`surface_mesh.rs`): a reservoir of candidates covers the whole source and is thinned spatially to the vertex limit. Normals are estimated from neighbours and each neighbourhood is triangulated in its tangent plane, on several threads in bounded batches with cancellation between them. The orientation of faces is propagated across connected patches, short planar inner loops and well-aligned triangular gaps are filled, and the normals are recalculated from the final triangles. Independent neighbourhoods can still disagree, so the result is not watertight. The OBJ keeps a deterministic order of vertices and faces.
- **Closed mesh** (`surfels.rs` and `closed_mesh.rs` in the core, `closed_mesh.rs` in the desktop crate): the points of a region are reduced per half voxel to oriented surface elements, a signed distance is summed at the corners of a voxel lattice, gaps up to the hole limit are closed from coarser levels, and the surface is taken out by dual contouring, in tiles of 96 voxels that are meshed in parallel and join by voxel key. The desktop module follows the shape of `drawing.rs`: the settings with what the Options and Run steps of Mesh Pointcloud show of them, the job with its stages, the `mesh` command with the mode `closed`, `set_closed_mesh_settings` and the `--closed-mesh` mode; `main.rs` only holds the field, the message variant, the calls and the branch of the command line.
  - A job gets its scene when it starts: the layers (the active one, or every visible one that reaches the section box and holds no 3D BAG buildings) with their clouds, indexes, transforms and deletion masks, the class filter and the section box, which is the `region` of the core. The filter of the core gets the deletion masks and the classes only; a selection is not passed, because the core plans its work by the region.
  - The core returns the mesh in scene coordinates. `to_source` maps it to the frame of the scan that gets it, as the inverse of `mesh_export::in_scene` (positions through the inverse transform, normals scaled back, the corner order reversed for a mirrored scan), so the viewer and the mesh export, which both apply the transform of the layer, need no change and a later Move or Scale takes the mesh along. A file a job writes itself is written before that mapping, as the scene shows it.
  - Stations come from the cloud of a layer (`SurfelSource::new`, `SurfelSource::of_cloud`). A cloud from an index cache that does not know its scan ranges is cloned and read once with `PointCloud::read_scan_ranges` on the worker thread, written back to the cache with `OctreeIndex::open_cached_if_present`, and kept by the tool for later jobs of the session, keyed by the cloud of the layer. The worker hands the cloud over through the shared `Control` of the job and not in its result, so it is kept when the job is cancelled or fails after the pass. The tests reach that pass with `PointCloud::forget_scan_ranges`, a hidden method of the core that leaves a cloud as one from such a cache; the write-back to the cache is covered in the core only.
  - A layer without an index is read into memory with `region_source::resident_points`, up to 5,000,000 points; the core refuses a streamed layer. The command-line mode builds an index in a temporary folder for a larger file without a cached one.
  - The texts of refusals, of a setting that cannot be read or lies outside its limits, and of advice are `Sentence`s: English for the status bar, the command line and the API, and translated on the card. The limits of the three numbers are stated by the desktop from the constants of the core, in the words of `ClosedMeshConfig::validate`, which a test holds together. Counts in advice are written by a formatter the caller gives: grouped on the card and in Properties, plain on the command line and in the API.
  - A job is refused before it starts when the active layer has a scale of zero, since the mesh could not be mapped to its frame, and with every visible scan asked for when the active layer holds 3D BAG buildings, since the export would write a mesh of scans with the credit of the register. `run` checks the scale once more before it reads anything, so no file is written for a mesh that cannot be kept.
  - The estimate the Options step shows before a job is two triangles per voxel face of the six faces of the region (`box_triangles`, `fit`). With simplification it warns when that is above the limits, and says the job will stop when a fortieth of it still is. Without simplification every triangle stays and a scanned room has more of them than its box, about 1.4 times on a generated room with noise, a column and reveals: the Options step warns from two thirds of the limit (`SURFACE_MARGIN`) and says the job will stop above the limit.
  - Not verified: nothing was run on a real scan. The report of a job was looked at in a running window on generated rooms, in the Properties block of version 0.9.1 (`docs/images/closed-mesh.jpg`) and on the Run step of Mesh Pointcloud (`docs/images/mesh-pointcloud.jpg`); the strip during a job was only built in tests.
- A mesh is limited to 4,000,000 vertices and 8,000,000 triangles (`MAX_VERTICES` and `MAX_TRIANGLES` in `obj_mesh.rs`, exported as `MAX_MESH_VERTICES` and `MAX_MESH_TRIANGLES`): the mesh readers refuse a larger file, the writers a larger mesh, and a closed mesh job stops there. The numbers follow from the viewer: all meshes share one vertex buffer and one index buffer with 32-bit indices, a vertex is 48 bytes there, and the device takes no buffer above 256 MiB, so one mesh at the limit (192 MB of vertices, 96 MB of indices) always fits. `gpu_viewport::drawn_meshes` leaves out a mesh that does not fit beside those before it instead of asking the device for a buffer it would refuse, and the Surface mesh section of Properties says so. The 3D BAG client keeps its own limits of one and two million. Mesh export checks the indices before it touches the destination and saves atomically.
- **Mesh Pointcloud** (`desktop/src/mesh_wizard.rs`): the card of the one button of the SURFACE group, with the steps Method, Options and Run. It holds no settings of its own: the closed mesh and the faces keep theirs in `closed_mesh.rs` and `faces.rs`, which give the card their fields (`closed_mesh_options`, `faces_options`), what a job would do (`Notes`) and how a job runs or ended (`RunState`); the 3D surface keeps `surface_settings` in `main.rs`, and the card keeps how the last terrain mesh and the last 3D surface ended, each apart (`FileMeshLast`). The Run step finds the scan that holds the result it shows by the identity of that mesh or those faces (`MeshOf`, `FacesOf`), so **Show in model** and **Export…** act on that scan whichever scan is active, and wait when none holds it any more. So a method keeps its options when another is chosen, and the commands of the API that set them and start the jobs are those of before. What the methods work on (`Scope`) is worked out again after a message only when a print of the scans, their deletions and selections, the classes shown and the section box changed; the points inside the box are the share of the overview sample of a scan inside it, applied to all of its points. `mesh_wizard` of the API shows the card on a step.
- **Mesh export** (`mesh_write.rs` in the core, `mesh_export.rs` in the desktop crate): `write_mesh` writes OBJ, binary PLY with double coordinates and binary STL. STL holds 32-bit floats, so an axis with coordinates beyond 2,048 m is written relative to a whole-metre origin that the header names and the STL readers of the core add again. The desktop module holds the save dialog, the `export_mesh` command, the `--mesh-export` mode and the Properties section of a mesh; it applies the transform of the layer to the positions and the normals before writing, and reverses the corner order of the triangles when the scale mirrors the layer, so the file keeps its outside (`in_scene`). A 3D BAG layer gets the credit of the register as comments, in ASCII for PLY, whose writer refuses other characters; `is_bag3d_mesh` in `main.rs` finds the credit again in the leading comments of an OBJ file and in the header of a PLY file.
- **Mesh figures** (`mesh_quality.rs`): `mesh_topology` counts open edges and connected parts by sorting the edges and compares vertices by index, which is right for a mesh from one of the mesh jobs. `mesh_topology_by_position` counts vertices at the same position as one and is used for a mesh read from a file, where a vertex can stand once per face corner or once per material colour (the OBJ reader splits those itself). The desktop runs the count on the worker thread that made or read a mesh and keeps the result with the layer. `mesh_deviation` and `mesh_simplify.rs` are used through the closed mesher, which measures the distance from a sample of its points to its result.

## Detected faces

- **Core** (`core/src/surfaces/`): `detect_surfaces` reads the points of a region twice through `region_source.rs`. The first pass makes the working set of one mean per voxel (`voxel_cloud.rs`), on which normals are estimated, flat regions are grown and fitted (`segment.rs`) and cylinders are looked for among what is left (`cylinder.rs`). The second pass, with the leaves read in parallel, measures every raw point against its face and counts it in a grid in the plane of that face (`chart.rs`), from which the outlines are traced through `grid2d.rs`; `edges.rs` finds the lines faces share and puts the outline corners on them. `export.rs` writes the OBJ and the JSON and builds the two meshes of the viewer. The result holds scene coordinates for the placement of the anchor layer, which it states; `DetectedSurfaces::placed` gives the same faces for another placement.
- **Desktop** (`desktop/src/faces.rs`): the settings with what the Options and Run steps of Mesh Pointcloud show of them, the job with its stages, the layer of faces a scan keeps, the list, the highlight, the exports, the seven commands and the `--faces` mode. `main.rs` only holds the field, the message variant, the calls, the field of `CloudEntry` and the branch of the command line. The module follows the shape of `closed_mesh.rs` and uses its helpers: `Sentence`, `Layers`, `number`, `choice_list`, `box_limits`, and the pass that learns which station measured each point (`with_scan_ranges`), whose answers both tools keep in one place (`ClosedMeshTool::stationed`, `keep_stations`).
- The limits of the three numbers of the options (1 to 500 mm, 1 to 45 degrees, 0.01 to 10,000 m²) are stated by the desktop: the core asks for a tolerance and an area above zero only. A test runs the ends of the ranges through `SurfaceDetectConfig::validate`. Everything else of the config is the default of the core.
- A job gets its scene when it starts: the layers (the active one, or every visible one that reaches the section box and holds no 3D BAG buildings) with their clouds, indexes, transforms and deletion masks, the class filter, the section box as the region, and the place of the active layer in that list as the anchor. With every visible layer asked for, the active layer has to be among them, because the result is stated for its placement. A layer without an index is read into memory with `resident_points` when it has at most 5,000,000 points, and is streamed from its file twice otherwise.
- The result is kept as `CloudEntry::faces`, a `FaceLayer`: the faces as found, the same faces for where the scan stands now, the two meshes in the source frame of the scan, the colouring, the switch, the highlighted face and what the faces were made from. The meshes are in the source frame, so the viewer places them with the transform of the layer and a move or scale needs no new mesh. `settle_faces`, which `update` calls after every message, re-places the listed faces when the transform of their scan differs from the placement they hold for (the meshes are rebuilt only when a scale unequal along the axes drops the cylinders, or brings them back), and marks the layer stale when a scan it was made from has another deletion mask, another index than the one it was read through (a first index of a scan read without one holds the same points and does not count), or is gone, and, for faces made from several scans, when one of them has another transform than at the time of the job: the faces follow the scan that keeps them, the points of the others do not. It compares by identity, as `settle_drawing` does, so no handler has to remember to do it; once stale, the layer drops what it compared with.
- The viewer draws the faces as one more mesh through the buffers all meshes share. `gpu_viewport::shown_meshes` lists, per layer, its mesh and then its faces; `drawn` passes that list through `meshes_that_fit`, so faces that do not fit beside the meshes are left out like a mesh, and `drawn_meshes` and `drawn_faces` tell Properties which were. The mesh that is shown is part of the key of the buffers and of the scene, so a switch of the colouring or of the Faces checkbox rebuilds them and a refinement of the points does not.
- The highlight is drawn on the canvas over the points, without a depth test, as the preview of a section drawing is: the rings of a plane cut off at the viewport and filled by the even-odd rule (`drawing::screen_ring`), with the outline drawn edge by edge, and a cylinder as lines along its scanned part (`cylinder_edges`).
- Exports take the faces for where the scan stands (`placed`), on a worker thread; the JSON names only the file name of the scan. The list of the local API is the same document without the outlines unless they are asked for.
- Not verified: nothing was run on a real scan. The list and the colours per face were looked at in a running window on generated rooms, with the list in the Properties block of version 0.9.1 (`docs/images/detected-faces.jpg`); the deviation colours and the highlight were only built in tests. The command-line mode was run on generated rooms of 5.8 million points; the figures are in the user guide.

## Section drawings

- **Core** (`core/src/drawing/`): `slab.rs` takes the slab behind one face of the section box and reads its points in one pass through `region_source.rs` (the octree leaves that touch the slab, or the whole source of a layer without an index), thinning them on the cut plane and counting them in a grid. `outline.rs` traces the filled cut from that grid. `section.rs` has the two entry points the desktop calls, `export_section_drawing` and `preview_cut_regions`, and `write.rs` writes the drawing model of `mod.rs` as DXF or DWG through the codec crate, atomically. The defaults and limits are constants of `mod.rs`; `DrawingRequest::validate` refuses what is outside them, it does not clamp.
- **Desktop** (`desktop/src/drawing.rs`): the choices of the Properties block, the job with its progress and cancel, the preview overlay, the `export_drawing`, `preview_drawing`, `clear_drawing_preview` and `cancel_drawing` commands and the `--drawing` mode. `main.rs` only holds the field, the message variant, the calls and the branch of the command line.
- A job gets its scene when it starts: the section box, the visible layers with their clouds, indexes, transforms and deletion masks, and the class filter. The worker builds the sources of the core from it, and its filter gets the position of a layer in that list, so the masks stay in the order of the layers.
- The preview keeps the scene it was made from. `settle_drawing`, which `update` calls after every message, compares it with the window (section box, visible layers by identity, transforms, deletion masks, classes, and the settings the cut depends on) and drops the preview when they differ, so no handler has to remember to clear it. A preview job whose scene has changed is cancelled the same way.
- Progress goes through a few atomics that the worker writes and a poll reads four times a second; the line of the strip above the scene comes from `DrawingTool::progress_line` (`Phase::Drawing` in `open_progress.rs`). Cancel is the progress callback of the core returning `LoadError::Cancelled`.
- The command-line mode uses an index from the cache when there is one and never builds one.
- The overlay is drawn on the canvas over the points, without a depth test. Every ring of a region is cut off in front of the eye and at the viewport with a margin (`screen_ring`), and the rings of a region are filled together by the even-odd rule, so the fill stays when a walking camera stands inside a region or the view is zoomed in on one wall. The outline is drawn edge by edge with the edge clipping of the measuring tool, not as a stroke of the filled shape, which would show the edges the cutting off adds.
- A job is refused before it starts while a visible layer holds a provisional cloud (one that is still being imported): the core would refuse it only when the read reaches that layer, and would leave it out without a word while its bounds do not reach the slab.
- The job reports the depth of the slab that was drawn (`slab_depth`, from `slab_from_section` of the core), not the thickness asked; the status line and the block say so when the box made it less.
- Not verified: no written file has been opened in a drawing program, and nothing was tried on a real scan. The tests read the DXF text and use the DXF reader of the core. The block and the preview of a plan were looked at in a running window on generated rooms (`docs/images/section-drawing.jpg`).

## 3D BAG client

`bag3d.rs` follows the pages of the 3D BAG API, applies the CityJSON transform of each page, triangulates polygons with holes and writes a georeferenced OBJ with the attribution of the register. One download is limited to a hundred pages and to the mesh limits above. The panel's map (`bag_map.rs`) draws raster tiles of the Kadaster background map served by PDOK, in RD New. The tests of both are offline.

## Local command API and MCP server

The window starts a token-protected command server on the loopback address (`native_api.rs`); `--mcp` runs a server on standard input and output that offers the same commands as tools (`mcp/`). A new command needs its row in [API.md](API.md), its tool, and the tool's row in [MCP.md](MCP.md). The tests fail when a row of API.md has no tool or when MCP.md and the list of tools differ; a command that has neither a row nor a tool is not caught, so add all three together.

## Command line

`cli_help.rs` holds the one list of modes that `--help` prints. A new mode is an entry there, its branch in `main`, and a row in the command-line table of the root README.

## Open CAD Studio

Every package carries Open CAD Studio, the program that `cad_viewer.rs` opens exported DXF and DWG files in. Its source is not part of this repository. [`packaging/open-cad-studio.pin`](packaging/open-cad-studio.pin) names the one commit of its repository that is built, with four lines: `url`, `commit` (the full hash), `tree` (the hash of the tree of that commit) and `date`.

```bash
bash packaging/build-open-cad-studio.sh -j 4                 # target/open-cad-studio/release/OpenCADStudio
bash packaging/build-open-cad-studio.sh --target aarch64-apple-darwin
bash packaging/build-open-cad-studio.sh --fetch              # only fetch and check the source
```

The script fetches that commit alone (`git fetch --depth 1 URL COMMIT`) into `target/open-cad-studio/source`, a git repository of its own, and stops before anything is built when the tree it got is not the pinned tree, the date differs, a git dependency in its `Cargo.lock` names no full commit hash, or its `LICENSE` is not the GPL-3.0 text that the packages carry for it. A checkout already at the commit is used without fetching; files changed in it by hand are restored first. `OCS_FETCH_FROM` fetches from a local clone or a mirror instead, checked the same way, such as the bare repository with only the pinned commit that `--export FOLDER` writes; the Packages workflow hands the commit to its builds that way. `OCS_VENDOR_DIR` names the crates that `archive-open-cad-studio-source.sh` vendored for the commit (the folder `vendor/` of its release file, or `target/open-cad-studio/vendor`): Cargo then builds them in place of their git repositories, and a folder vendored for another commit is refused. The source is built as it is, with no change of our own: `cargo build --locked` builds the commit of every git dependency that its `Cargo.lock` names, also for a dependency that follows a branch, so nothing moves on by itself. Cargo runs in the source folder, so that its `.cargo/config.toml` applies (the stack size of the program on Windows, and of `rustc`), with `--release`, only the binary `OpenCADStudio` and the target folder `target/open-cad-studio`; other options go to `cargo build`. Run again with nothing changed, Cargo has nothing to do. The build script of the program reads its revision from that checkout, so the program reports the pinned commit.

On Linux it needs the libraries listed in the root README and a C++ compiler, for a mesh library of the program; the binary then links the C++ runtime, which `packaging/linux/check-binary.sh` allows up to the symbol version of the oldest supported systems. A release build with `-j 4` from an empty target folder, with the crates already downloaded, took 27 minutes (Rust 1.94, `x86_64-pc-windows-gnu`, on a development machine with 32 threads); the program is about 125 MB. Built with the GNU toolchain on Windows it links `libstdc++-6.dll` of MinGW; the script copies that library, and the libraries it needs in turn (`libgcc_s_seh-1.dll` and `libwinpthread-1.dll`), from the folder of `g++` to beside the program, so that it starts from a development build also where MinGW is not on the search path. The Windows packages build it with the MSVC toolchain, as they build the application, and need none of them. A package carries neither these libraries nor their licences, so `packaging/build-archive.sh` and `packaging/check-open-cad-studio.sh` refuse an `OpenCADStudio.exe` that loads them: for a local package, build it with `--target x86_64-pc-windows-msvc`, which writes `target/open-cad-studio/x86_64-pc-windows-msvc/release/OpenCADStudio.exe`.

`cad_viewer.rs` uses that program before the one chosen in Settings: beside its own executable (Windows, the archives, the macOS bundle), in `../lib/open-pointcloud-studio` (the `.deb` and the AppImage), and for a development build in `target/PROFILE/` in `target/open-cad-studio/release/`. A program inside a mounted AppImage is copied to the cache folder before it is started, because the mount goes away with the application; the copy has one place for every version (`open-cad-studio/`, with a file `version`) and is replaced when the version or the size of the program changed, so that copies do not pile up and what the viewer registers with the desktop keeps pointing at a program. The viewer is started without the variables of the AppImage runtime (`APPIMAGE_VARIABLES`), which it would otherwise take for its own: it writes the program `APPIMAGE` names into the desktop entries it makes for itself. The tests do not look beside the test program: `BUNDLED_IN_TESTS` stands in for what is found there.

`packaging/archive-open-cad-studio-source.sh` writes the source of the pinned commit for the release page, as `open-cad-studio-source_SHORT.tar.gz`, and the crates its `Cargo.lock` takes from git repositories, as `open-cad-studio-vendor_SHORT.tar.gz`: Open CAD Studio is GPL-3.0 and some of those crates are MPL-2.0 or LGPL, and whoever gets it from a release can get all of that source from there. The crates are vendored with `cargo vendor --locked --versioned-dirs` into `target/open-cad-studio/vendor`, with a `config.toml` that puts them in place of their git repositories; unpacked in one folder, the two archives build with `cargo build --release --locked --bin OpenCADStudio --config vendor/config.toml`. The script refuses to write them unless `packaging/OpenCADStudio-NOTICE.txt.in` names every git repository with its commit and every crate from one with its version and licence, and both notices name every crate under a copyleft licence without a permissive alternative; a new pin needs those lines. [packaging/README.md](packaging/README.md) says how the packages carry it and how the pin is moved to another commit.
