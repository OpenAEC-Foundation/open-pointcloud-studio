## Workspace

The workspace has two crates:

- `core` (`pointcloud-core`, LGPL-3.0-or-later): readers and writers of the file formats, the octree index on disk, streamed reads of the source and of the index, export, the meshers and the 3D BAG client. It has no user interface.
- `desktop` (`open-pointcloud-studio-native`, GPL-3.0-only): the `iced` application with its `wgpu` viewport, the tools, among them box selection and point picking (`selection.rs`), the settings, the local command API and the MCP server. Its binary is `open-pointcloud-studio`.

The version is written once, under `[workspace.package]` in `Cargo.toml`. No HTML, CSS, JavaScript or web view is used.

## Running and testing

```bash
cd native
cargo run -p open-pointcloud-studio-native                      # the window
cargo run -p open-pointcloud-studio-native -- /path/to/scan.laz # with a file
cargo run -p open-pointcloud-studio-native -- --help            # every command-line mode
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

A development build compiles `pointcloud-core` and the `las` and `laz` crates with optimisation (see the profiles in `Cargo.toml`), so that large scans stay usable while developing. The full-source loops of the readers, the exporters and both meshers live in `core` for that reason: the desktop crate passes in predicates and progress callbacks and does not recompile those loops at its own lower optimisation level.

Three benchmarks are examples of the core:

```bash
cargo run -p pointcloud-core --example visit_bench -- FILE 2000000   # read the first points of a file
cargo run -p pointcloud-core --example lod_bench -- FILE.laz 80000   # a level-of-detail sample from an index
cargo run -p pointcloud-core --example surface_bench -- FILE.laz OUTPUT.obj
```

Test data is generated by the tests or comes from public data sets. [TEST_DATA.md](TEST_DATA.md) lists the public ones and how to fetch them. Nothing of a real project goes into the repository: no scans, no screenshots of them, no file names or places.

Tests that hold documents to the code:

- `cli_help.rs`: the list of command-line modes against what `main` handles, and the table in the root README against that list.
- `mcp/tests.rs`: every command listed in `API.md` has an MCP tool, and `MCP.md` lists exactly the tools, in order.
- `i18n.rs`: every translated text in the source has an entry in every language table, and no entry is unused.

The two tests marked `live_services` ask the real 3D BAG and map services and are skipped by default; [TEST_DATA.md](TEST_DATA.md#checking-the-3d-bag-and-map-services-before-a-release) says when to run them.

## User interface

- **Ribbon.** All tools are on one ribbon without tabs, and every action appears there once. Small tools stand in three rows. The ribbon measures its scrollable content, so the arrow buttons appear only when groups are cut off and go away when the window is wide again. The cancel action of a running selection, scale, mesh or index build takes the place of its start button or appears only during the job.
- **Rarely used commands** are in the File view (`file_view.rs`). Properties holds the settings and the lists of what is in use; of the ribbon's actions it repeats only Save for a view, Clear for a measurement and the cancel button of a running mesh or scale job.
- **Texts.** A text is written in English in the source and passed through `i18n::tr`; `i18n::key` marks a text that is translated where it is shown. Other languages are tables from the English text in `assets/locales/`, and a text without an entry stays English. A counted text is an entry with `{name}` marks that are filled in when it is shown; a translation keeps the same marks. A further language is one JSON file beside `nl.json` and one line in the table of `desktop/src/i18n.rs`; only the `set_language` rows of `API.md` and `MCP.md` name the language codes by hand. Status messages are not translated.
- **Settings files.** `preferences.rs` reads and writes `settings.json` (colour mode, point size, eye-dome switch and strength, station markers, point budget, auto-index). A change from the ribbon or the API is saved after a short delay, and invalid stored numbers fall back to the defaults. The theme and the language are each one small file, and `extensions.json` lists the extensions that are switched off, so a missing or damaged file enables everything. The user guide names the folders.
- **Window.** On X11 the application sets the light or dark hint of the system title bar to match the theme; on Windows the title bar takes the colours of the theme (`native_chrome.rs`). On Linux the window announces the application id `org.openaec.OpenPointcloudStudio`, the name of the desktop entry. On macOS, files handed over by the system are opened like dropped files (`macos_open.rs`).
- **Dialogs.** File dialogs use `rfd::AsyncFileDialog`, so the window stays responsive while the dialog of the system is open.
- **Layer identity.** Preview and index jobs, meshing, deletion and Undo and Redo are matched to the layer they belong to, not to its file path.

## Reading and writing

- LAS and LAZ open from the header, with a bounded preview that samples spaced ranges without decoding every point. Other formats are read in full once to learn bounds and counts. At most 100,000 preview points are kept per file; a source of 512 MiB or more that is shown while it is read keeps up to two million.
- Full reads of LAS and LAZ use bounded batches: 400,000 points per request for LAZ, so that the parallel decompressor handles several compression chunks at once, and 16,384 for LAS. Callbacks still receive the points in source order and can cancel inside a batch.
- LAZ is written with the parallel compressor of the `las` crate in batches of 400,000 points. A same-format LAS or LAZ export without edits copies the source bytes. Conversions and filtered or transformed exports write the original LAS point records and keep the coordinate grid of the source.
- XYZ, PTS, CSV and both PLY variants are encoded in batches of 65,536 points on several threads and written in source order.
- Every export writes to a temporary file and publishes it under its name only after the whole source and the expected point count have been checked.
- E57 files are read through a buffered window (`window_reader.rs`), because the format is decoded in pages of 1 KiB and a seek per page is slow on a network share. `e57_quick.rs` takes the spread preview of a large file from evenly spaced data packets; `snapshots.rs` shows a large source while it is being read.
- The filtered E57 writer copies the selected raw records with the prototype and value types of each source scan. A new E57 file from another format, or a transform that cannot keep a valid scan pose, is written as one scan in world coordinates with XYZ, 8-bit colour and intensity.
- PCD `VIEWPOINT` rotates and translates every point in all three storage modes.
- A scan project file is a ZIP container whose XML document lists the scans; `project_open.rs` reads only that document, and reads folders and project files on a worker thread.
- The BCF file is a ZIP container written by the application itself (`bcf.rs`), with deflated XML and stored images.

## The index on disk

- The octree is built on several threads. A node is read in blocks of 65,536 of its fixed 40-byte records, which are assigned to the eight children in parallel and written in block order. Subtrees are built side by side on a bounded pool; large nodes are split one at a time so that the disk does not hold every level at once. The files are identical to those of a single-threaded build, which the tests keep as a reference, with exact source ordinals and cancellation between blocks.
- A finished index of a PLY, E57, PCD, PTX, XYZ, ASC, TXT, CSV or PTS file keeps the exact bounds, the count and the attribute flags of the source in a cache manifest that is written atomically. Reopening an unchanged file reads that manifest and a small preview from the octree instead of the source. A missing, stale or damaged manifest falls back to the full reader.
- E57 scanner positions come from the metadata of the file and PCD `VIEWPOINT` from its text header; neither needs point records. PTX scanner positions and axes are stored in the manifest, because each scan block has its own pose.
- `--index` on a file other than LAS or LAZ collects the preview and the metadata while it writes the root of the octree, in one pass over the source. With automatic indexing on, the window takes the same route for such sources of 64 MiB or more and shows the checked preview after that pass while the tree is still being built.
- Each leaf has a compact preview for level-of-detail reads. An index without them creates them on first use.
- A cancelled build removes its temporary files and publishes nothing.

## The 3D view and level of detail

- Points are drawn as lit sphere impostors with `wgpu`. Each sphere writes its curved front surface to the depth buffer, and point picking uses the displayed radius and that depth. Coordinates are rebased in double precision before they go to the graphics card.
- Mesh faces are lit with interpolated vertex normals; a mesh without normals gets them from its triangles, and a non-uniform or mirrored scale maps them into the scene.
- Eye-dome lighting is a screen-space pass that shades points and faces by the depth of their neighbours.
- The viewport keeps its geometry and its uploaded buffers across redraws that only move the camera. A change of visibility, level-of-detail points, colours, filters, edits or section limits rebuilds them. Points are uploaded in buffers of at most two million each.
- After the camera stops, the viewport chooses the visible octree nodes by their size on screen and reads a sample of at most the point budget. The sample on screen stays until its replacement is ready, and a request that the camera has overtaken is cancelled while it reads. Releasing a drag starts the request for the new view at once.
- Indexed clouds share the budget by how much of the screen each covers, and what one cloud cannot use goes to the others. The clouds are sampled in parallel on a bounded pool.
- For a budget above 500,000 points a first pass is read before the full sample. Its size comes from the read and build pace measured on this computer, with 250,000 points as the least (`lod_pace.rs`), and stays within what the nodes in view give from their previews. It is shown only when it improves on the sample on screen and is skipped otherwise.
- At 20 times zoom or closer the leaves in view are read exactly and only the points that fall inside the viewport are kept. A view that would need more than two million candidate points keeps the regular sample.
- Box selection visits the source points in the octree leaves that the box touches, or reads the whole source when there is no index. A selection is a compact bit set of source ordinals and keeps its bounds in source coordinates, so that Zoom selection needs no second read. Opening, hiding or removing a layer cancels a selection scan that is under way.

## Meshers

- **Terrain** (`mesher.rs`): every source point goes through a bounded grid in X and Y that keeps the lowest point per cell; the result is triangulated as a 2.5D mesh and long edges across gaps are rejected. The cap is 100,000 vertices.
- **3D surface** (`surface_mesh.rs`): a reservoir of candidates covers the whole source and is thinned spatially to the vertex limit. Normals are estimated from neighbours and each neighbourhood is triangulated in its tangent plane, on several threads in bounded batches with cancellation between them. The orientation of faces is propagated across connected patches, short planar inner loops and well-aligned triangular gaps are filled, and the normals are recalculated from the final triangles. Independent neighbourhoods can still disagree, so the result is not watertight. The OBJ keeps a deterministic order of vertices and faces.
- A mesh held by the viewer is limited to one million distinct vertices and two million triangles per file (`obj_mesh.rs`). Mesh export checks the indices before it touches the destination and saves atomically.
- **Mesh export** (`mesh_write.rs` in the core, `mesh_export.rs` in the desktop crate): `write_mesh` writes OBJ, binary PLY with double coordinates and binary STL. STL holds 32-bit floats, so an axis with coordinates beyond 2,048 m is written relative to a whole-metre origin that the header names and the STL readers of the core add again. The desktop module holds the save dialog, the `export_mesh` command, the `--mesh-export` mode and the Properties section of a mesh; it applies the transform of the layer to the positions and the normals before writing, and reverses the corner order of the triangles when the scale mirrors the layer, so the file keeps its outside (`in_scene`). A 3D BAG layer gets the credit of the register as comments, in ASCII for PLY, whose writer refuses other characters; `is_bag3d_mesh` in `main.rs` finds the credit again in the leading comments of an OBJ file and in the header of a PLY file.
- **Mesh figures** (`mesh_quality.rs`): `mesh_topology` counts open edges and connected parts by sorting the edges and compares vertices by index, which is right for a mesh from one of the mesh jobs. `mesh_topology_by_position` counts vertices at the same position as one and is used for a mesh read from a file, where a vertex can stand once per face corner or once per material colour (the OBJ reader splits those itself). The desktop runs the count on the worker thread that made or read a mesh and keeps the result with the layer. `mesh_deviation` and `mesh_simplify.rs` are not used by the desktop yet.

## 3D BAG client

`bag3d.rs` follows the pages of the 3D BAG API, applies the CityJSON transform of each page, triangulates polygons with holes and writes a georeferenced OBJ with the attribution of the register. One download is limited to a hundred pages and to the mesh limits above. The panel's map (`bag_map.rs`) draws raster tiles of the Kadaster background map served by PDOK, in RD New. The tests of both are offline.

## Local command API and MCP server

The window starts a token-protected command server on the loopback address (`native_api.rs`); `--mcp` runs a server on standard input and output that offers the same commands as tools (`mcp/`). A new command needs its row in [API.md](API.md), its tool, and the tool's row in [MCP.md](MCP.md). The tests fail when a row of API.md has no tool or when MCP.md and the list of tools differ; a command that has neither a row nor a tool is not caught, so add all three together.

## Command line

`cli_help.rs` holds the one list of modes that `--help` prints. A new mode is an entry there, its branch in `main`, and a row in the command-line table of the root README.

## Installer and packages

The Windows installer is built from [`installer/windows.iss`](installer/windows.iss) and the folder that `packaging/build-archive.sh` leaves behind:

```
ISCC /DAppVersion=0.8.0 /DSourceDir=..\target\packages\open-pointcloud-studio_0.8.0_windows-x64 installer\windows.iss
```

It writes `open-pointcloud-studio_0.8.0_x64-setup.exe`. Everything else about the packages of the three systems, their tests and the steps of a release is in [packaging/README.md](packaging/README.md).
